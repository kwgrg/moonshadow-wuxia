## 已复现的状态错误

以下使用独立内存 fixture，不是原版实机或自然通关。均未写入浏览器/用户存档。

1. **亡者继续跟随。** g19 获得蔷薇后，在 g20 连续 `choose(1)` 四次，状态变为 `gBad1/travel`、`forsake:true`，但 `flags.companion`、`partyNames`、`companions` 都仍含蔷薇。序列化后 `restoreState` 仍如此。她会随玩家从 m51 回 m49，直到 gBad1 完成才被清除。应由实际死亡/安葬收束清理自由跟随，而非等迟到解药结束。依据：`runtime.mjs` 的 repeatRefusal/completeQuest 与 [travel-party.mjs](../public/travel-party.mjs)。
2. **留庄与邀约不改变实际队伍。** g22 选“我明白”后，文本称真儿与蔷薇在庄中等候，但蔷薇仍跟去 g23；随后 g23 选紫轩，进入 g24 时队伍仍只有蔷薇，紫轩、眉儿从未实际加入。`chooseEnding` 仅根据 `forsake`/`firstWoman` 选结局，不能证明完成接人。
3. **普通救援战刷新会重刷已杀单位并保留逐杀收益。** g16 4敌战中，隔离 fixture 用真实 `cast(0)` 结算一个1HP目标后，银两150→165、经验0→25、剩3敌；保存恢复到 talk，银两/经验仍165/25；重新开始立即刷回4敌。新救援战应采用稳定敌ID、存活HP/清除记录、失败重试与结算账本；不要把现有普通战刷新行为写成新验收。

## 实际路线问题与最小拓扑提案

当前 `routes.mjs` 主要由历史任务邻接生成后段边。只读 `routeTo` 结果包括：`m61 → m16`、g16结束后 `m61 → m41`、g19后 `m69 → m51`、g23后 `m17 → m70`。这些是实际跨图边，并非下面建议的逐图行程。`VALLEY_DEFENSE_QUESTS` 只到 g15，因此到 g16 又放开了历史 `m61 ↔ m16` 推断捷径。地图门户列表是所有可能邻居，不等于当前均开放；例如正线登塔时并未实际开放邪线 m66↔m69 跳层，不能据门户列表误报串线。

优先只补 g16→g18，以稳定 g16/g17/g18 ID 为兼容锚点：

- **厅堂与地下分开。** 保留 m61 为厅堂；三拒后的破围若新证据确认为独立战，应在 g16 前插入。新增正线 `r_good_dungeon`，从 m61 的地下入口进入，独立放守卫区和紫轩囚处；不借用 r_cult_dungeon 或 r_evil_dungeon 的处决旗标/演员持久化。可复用本项目 cult-dungeon 石砌原画及真实mask，但需要按守卫数量重新校验容量。牢门是否必须玩家开、开门触发方式待核，不能因为旧 `object` 字段而自造钥匙。
- **紫轩必须实际送回。** 救出只提交 released + companion紫轩；下一节点目标 m16，候选路线为 `地牢 → m61 → 倚天山连接图 → r_hanbo_return → 小筑附近安置点`，到参考确认的安置点完成交谈才 settled + companion null。m16 已是独立室内且有原创 beimo-hero-room，可先使用其已有床前/门口；若参考证明另有内室，再新增正线客房 alias，不能为了增加图数伪装原布局。剧情常驻紫轩与现有邪线小筑演员必须分支隔离。
- **去南郊须从屋中走出来。** 候选原创连接为 `m16 → m17 → m49 → m41`，复用已走通的相邻道路；只作为网页空间设计，不称原版精确邻接。g17须以 settled 或明确旧档例外为前置。眉儿的后续行为按新参考选择独立离场或护送安置，不能预先断言二者等价。

救援窗口须封住历史 m61↔m16、m61↔m41 等直接捷径；门槛采用 earned flags，不能仅凭 visited 或游标超过某任务开放。安置前不能显示“已回小筑”；返回厅堂、出牢、房内退出仍要允许正常折返，防止把新门控做成不可退的单向传送。
