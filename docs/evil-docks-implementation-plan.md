### 现有门户与必须封住的历史路径

现有返回路径查询为：`m57 → gate → second → first → entry → path → m31 → m34 → m40 → m41`。它保留层序，但不能凭“目的地在码头”保证途中参加新事件。

在当前邪线 e08 状态，已观察到下列通行边：

- `m29(剑气峰) ↔ m30(海边小屋)`，来自a42的历史推断。
- `m40 ↔ m41`，来自a56，且没有船行描述。
- `m40 ↔ r_evil_ferry`，此前回岛的倚天山航线仍开放。
- 较旧公共图还有 `m42 ↔ m43`、`m48 ↔ m49`，需要按完整可达图审查，不能仅凭地名把所有边都归为海岛边。

实际 e09 路径查询还能得到 `m31 → m30 → m29 → m49`，这是新岛战和两码头最直接的绕行风险。

建议为“接受招揽后至紫轩结果完成”的邪线窗口建立明确的通行约束：

1. 先完成逆向禁地与入口插叙，才允许村内求援/开战。
2. 战中禁出口；未清36人不可到送别节点；送别未完成不能启航。
3. 在本窗口对全部实际可达的离岛边检查前置，封住历史公共道路及倚天旧航线绕行。不能仅删 `m57↔m41` 或仅锁新边。
4. 码头→内陆的出路须有“紫轩结果完成或明确旧档历史结果”条件。
5. 下一日之前的落叶谷目标须有“庄内夜间段完成或旧档夜间历史”条件。
6. 上述约束只作用于本段邪线；正线、过去章节和之后正常回访应保留。`visited`、数字任务索引和无关done不能替代新段的实际前置。
7. `exitsFor()` 目前把所有boat固定命名成“去忘忧岛/返回倚天山”，需要由边提供双向label，才不会把中原码头航渡错误标成返回倚天山。

路线性能边界：`routeNeighbors()`目前把4个when条件旗标枚举为16种组合。若照现模式增加紫轩两旗标、送房两旗标，会扩大到256种组合，且每张图重复枚举。下一步应至少缓存同一任务表的候选邻接，或对互斥答案枚举合法组合；不要把每个剧情里程碑再放进when导致进一步扩张。实际前置应继续放requiredFlags/显式路线gate。此处只是规模核算，尚未测量新版本启动时间。

## 4. 运行时接口：哪些能复用，哪些尚缺

### 4.1 楼中交锋应是旁观插叙

现有 `skirmish-runtime.mjs` 总把hero加入敌方目标，且主角死亡直接失败。不要把它直接作为第二次摘星楼交锋。最小方案是独立临时场景配合已有 move/face/strike/fallen/hide步骤，清楚表达两名人物交锋及纳兰倒下的叙事结果；数值胜负和动作均标为网页编排。

两梦已验证的sceneKey隔离/白名单/恢复校验可以复用架构，但新增中性 `getStagingScene(key)` 或等效转接，保留两梦行为；不要把towerInterlude登记为weddingDream/lakeDream。当前 renderer 主画面和小地图都无条件绘制hero；`hide`给hero.hidden赋值并不能完成隐藏。需要明确的演出可见性契约，例如根据当前白名单scene定义派生 `hidePlayer:true`，同时屏蔽hero画面、小地图、标签和跟随实体。退出插叙必须恢复现实脚点/朝向、同伴，不把楼坐标写成真实世界位置。

`sceneKey`、演员站位、显隐、动作阶段和结果cue都要可恢复。结果旗标只在插叙release后提交；非法scene/前置不符应回真实安全点，不能直接给“纳兰死亡已播放”标记。主角不能攻击插叙人物、获得击杀经验或被镜头中的挥击扣血。

### 4.2 村落36敌全清

可复用 `s.skirmish={questId,defeatedIds,finished,failed}` 及稳定单位ID、当前HP/蓄力/玩家冷却的恢复。建议阵容明列35个普通强盗ID和1个强盗头目ID；所有人参与同一全清条件，没有原版分波依据。

当前缺口与最小扩展：

- `baseUnit()` 的外观/数值按cult两阵营硬编码。增加entry的npcCell、sprite、role、HP等显式配置，防止把月眉儿渲染成无忧教男弟子，把强盗头目渲染成别派人物。新数值、阵型、AI和难度均为网页原创。
- `startSkirmish()` 用通用左右格网取位，报错也写死“武当战场”。新村内需给独立可达spawn/heroStart，并确认36人不堆到同一nearestOpen格；开始几秒有可判断的安全距离。
- 月眉儿目前仅是跟随坐标，没有HP、攻击或失败状态。若表现共同作战，应将她接为稳定ally ID并隐藏装饰跟随分身；战后把存活单位接回跟随，不留下两个角色。
- 参考绑定了同伴死亡到主角死亡处理，但未实机核定失败画面。可实施“关键同伴倒下即本战失败”的网页规则（显式criticalAllyIds/failOnAllyDefeat），并标清恢复界面是网页设计。不能用当前任意allies倒下也不失败的逻辑冒充原版同伴机制。
- `markSkirmishDefeat()`已有去重，但必须只接受当前阵容且HP归零的敌方。恢复时核验ID集合、重复/空单位、失败优先于同tick全清。39人武当的旧保存不能被当作36人岛战。
- 战斗中begin/complete/travel/retry边界要保留；击败头目时若还有一个普通敌人，不能转送别。主角或关键同伴死亡，药品/关闭面板/普通对话不得解除失败。
- 全清恢复生命、内力、体力应在一次结果提交中执行，不应在每次读取after或回访时免费治疗。`applyEffects`当前只支持旗标、好感、善恶、技能、物品、同伴，没有通用recover接口，可新增声明式一次恢复效果。
- 现skirmish逐人不发金钱经验；普通battle的cast逐人会发。优先维持本战无逐敌结算的网页规则并明确记录，避免通过重开刷钱。原版是否存在其他掉落本轮未核，不能把该网页取舍说成原版无掉落。
- `completeQuest()`仍会给battle/boss两类药各1。新增显式默认补给开关或结算策略，岛战关闭这条隐式奖励；重试完整重开还是局部检查点必须明确。建议沿用已有完整重开，但死亡账本/HP在刷新时保持，不能刷新复活或重刷敌人。

### 4.3 紫轩固定死亡事务

现有e06结果拆分、requireStaging、exclusiveFlags、step.when和持续倒地演员可以直接作为模式，不需要把紫轩做成敌人或boss。

- e08只记录选择，例如evilZixuanDecision + 独占evilZixuanKill/evilZixuanRefuse；沿用网页索引0拒1杀，不套原变量索引。
- 选择按钮应即时提交并保存，再开始对应结果任务。当前journey普通选择要先读完option.after/q.after才choose；最小改法为新菜单移除含结果的after，把所有后果交给下一结果stage。若保留答复对白，则需像现refusal分支一样先commit。
- 结果任务复用 `strike → pose:fallen → cue → release`。拒绝支可以画月眉儿的原创动作，文档须保留原记录只有朝向/淡出/倒地的边界；不能声称动作帧与原版一致。
- `evilZixuanDead`只在结果完成时设置；其他结果任务被when过滤。保存选择后不重问，保存挥击后不重算善恶，保存倒地后不复活。
- 持久倒地展示同时要求结果完成旗标与相应staged标记。两结果使用相同角色身份但不得叠两具尸体；返回码头无可对话活紫轩，无普通战斗击杀奖励、物品掉落或玉佩遗书。
- 结果前后月眉儿通过演员/跟随互斥保持唯一。旧档只有历史死亡结论时另走显式legacy展示，不伪造新的staged完成。

### 4.4 回庄与夜间支路

多数动作可复用现staging。缺口主要是地图、房间出入口、阶段前置与通常NPC交互。

- 报告、第一次醒来、花园选择、不送后的第二次醒来/再遇/入室须各有可保存状态。不能仅存e09菜单答案后直接advance到e10。
- 每次开场前先验证地图和旗标；新房间无法从m49对话直接完成。外出次序不由visited或任务索引代替。
- 次日解除跟随与留庄状态一次提交，例如evilMeiStaysAtManor。当前stagingActor普通点击只显示“没有新的交谈”，需要增加无奖励常驻NPC对白入口；不能把一张可见立绘算作“通常交互人物”。
- 留庄演员何时离开由后续事件的明确旗标决定，不能永久重生；同时避免与e12的主线月眉儿NPC重复。此处只规划接口，不扩写e10以后剧情。
