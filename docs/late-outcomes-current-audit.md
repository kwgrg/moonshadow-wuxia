# 后段结果与存档现状审计（revision 13）

2026-09-24。受审基线为提交 `228a84a` 的后段实现，任务序列仍为 209 项；审计期间出现的救援场景美术文件未参与本报告。范围为善线 g16–g24、gBad1/gBad2 和邪线 e14 的奖励、分支、失败、存档及 UI 提交顺序。本轮只读产品与现有文档，不访问原版目录，不修改产品或正式测试。

证据来自代码与最小内存重放：人工章节夹具、边界 HP、真实 GameEngine 方法，以及现有 `validate-story-ui.mjs` 的内存 DOM 桩执行生产 `journey.js` 处理函数。DOM 桩不是浏览器；没有声称手动从开局通关、完整复刻、原版精确时序或画面验收。历史[后段审计](late-story-audit.md)中的压缩流程说明仍有参考价值，但其中已经被后续专章替代的旧缺口，不应当成当前未实现清单。

## 已复现的正常路径问题

### 1. 四拒后已亡故的蔷薇仍作为活人跟随；解毒后也没有按对白留庄

位置：`public/late-story-revisions.mjs` 的 g19、g20、g22、gBad1，以及 `public/travel-party.mjs:3`。

由 g19 选项取得蔷薇同行后，g20 四次拒绝只写 `forsake=true` 并转 gBad1。蔷薇仍在 `flags.companion`，读档不清除；抵达 gBad1 / 悲魔山庄时 `companions` 实际仍返回蔷薇。此时 gBad1 的前置纪事已经叙述她亡故、安葬和主角独返，实际画面角色与当前网页对白矛盾。必须读完 gBad1 才由其奖励清除同行。

另一条正常路径中，g22 的选择对白明确让真儿和蔷薇在山庄等候，完成后转 g23 / 樱花谷，`partyNames` 仍是 `[蔷薇]`。两种 g23 选择都不改变这一状态；前往 g24 时仍只有蔷薇随行，而紫轩/眉儿的同行仅出现在纪事文字与最终名单。

最小重放：g20 从 `companion=蔷薇`、choice 阶段开始，每次 `choose(1)` 后序列化并 restore；第 4 次得到 `gBad1 / refusals=4 / forsake=true / partyNames=[蔷薇]`。设置抵达任务图的普通旅程夹具后，`companions` 仍含蔷薇。g22 的 `beginObjective(); choose(0)` 也得到 `g23 / partyNames=[蔷薇]`。

建议检查：在明确的离场/死亡提交步骤前后逐步存读档；断言实际渲染入口 `companions`，不能只断言 `companion` 的最终清空。修复时应依据后续参考确定死亡与离场时点，不凭本审计擅定新的原版事件顺序。

### 2. g20 第四次拒绝在结果对白结束前没有提交

位置：`public/journey.js:62–80`、`public/runtime.mjs:325`。

g20 使用 `repeatRefusal`，没有走已经为招揽 `refusalRule` 设置的“先提交答复、再播结果对白”路径。现有 UI 在选项结果全部读完后才调用 `engine.choose()`。内存 UI 重放中，已有 3 拒时点击第 4 次拒绝，屏幕已显示拒绝答复，但 live state 与本地保存仍为 `refusals=3`、`phase=choice`、未设 forsake；将当时保存交给 restore 后仍回 g20，玩家可重新选择留下。只有读完结果对白才保存第 4 次并进入 gBad1。

这不是“前三次拒绝仍可接受”的规则问题，而是已点下的本次答复在显示结果后仍可被刷新静默撤回。前三次和接受选项也采用同样的延迟事务模式。

建议检查：每个拒绝次数的选项点击后立即读取存档，并在第一句/末句之间刷新；验证所点答案、计数与分支一致，且不会再次扣好感。若保留可撤回设计，应明确提供撤回答复操作，不能把刷新作为隐式撤销。本轮仅记录，未改事务或时序。

### 3. g23 的“先与月眉儿交谈”目前只是菜单标签，实际已先与紫轩对话

位置：`public/late-story-revisions.mjs:155–161`、`public/journey.js:87`。

当前 g23 只有紫轩主 NPC，内存枚举的角色交互目标也只有紫轩。生产 UI 必须先播放 g23.before 中紫轩和影枫的完整交谈，才显示“先与谁开口”的选择。因此选择“先与月眉儿”时，已经和紫轩谈完获救、解药与归隐；界面行为与选择问题相互矛盾。

这不会在正常状态下把结局算错：选 0 确实写 `firstWoman=zi`，选 1 写 `firstWoman=mei`，分别对应四美与三美结局。但它尚未实现由玩家实际接近、先后和两名角色交谈来决定分支，也没有两位角色各自的后续去留动作。

建议检查：两名人物都作为真实场景交互目标，从没有任何谈话记录开始分别先访问一人；记录首次谈话时点，途中读档与再次交谈不得覆盖；剧情必须遵循该先后而不是先播放另一人的固定对话。场景呈现需另做真实浏览器验证。

### 4. 普通战斗败北重试仍可重复获得同一批敌人的收益

位置：`public/runtime.mjs:370`、`:436`、`:448`，受审段包含 g16、g17、g18、e14；这是既有通用普通战斗缺口，不是本轮新引入。

最小重放先以边界 HP 夹具令一名普通敌人被生产 `cast(0)` 击败；随后主角 HP 设为 1，经生产 `hurt()` 和 `tick()` 实际进入败北事件，再调用再战动作。再战保留已经获得的钱与经验，同时恢复完整敌群；再次击败相同序号的敌人又给相同收益。

| 任务 | 第一次击杀后 | 败北重试后存活敌人 | 再次击杀后 |
| --- | --- | --- | --- |
| g16 | 165 银 / 25 当前经验 | 4 | 180 银 / 50 当前经验 |
| g17 | 165 银 / 25 当前经验 | 3 | 180 银 / 50 当前经验 |
| g18 | 165 银 / 25 当前经验 | 4 | 180 银 / 50 当前经验 |
| e14 | 165 银 / 25 当前经验 | 4 | 180 银 / 50 当前经验 |

起点均为 150 银、30 级、0 当前经验。`claimedRewards` 全程为空，说明任务一次领取账本不覆盖逐敌收益。未将直接在胜利后调用内部 retry 的结果算作玩家可复现漏洞；单首领 g24/gBad2 不能据这组用例推断同样的正常败北刷法。

同一败北快照恢复时，普通战斗由 `battle / HP0 / paused=true` 变为 `talk / HP1 / failure=null / paused=false`，战斗进度重置但资源仍保留。该行为不推进任务，但没有像已独立实现的阵营战那样保持失败与完整阵容证据。

建议在确定全局奖励设计后测试：部分击杀 → 败北 → 重试/刷新 → 相同敌人再败，不允许意外追加可刷的剧情收益；可采用整战统一结算或显式逐敌领取账本。依主任务要求，本报告只保留问题，不扩大为本轮全局重构或新增全局测试。

## 终局证据和不完整存档的保护缺口

以下需要人为构造缺失/矛盾状态或直接调用内部 API，不能冒称正常玩家已经绕过战斗或自动改错分支。

`completeQuest()` 对普通 battle/boss 没有像 skirmish 那样检查胜利记录和 after 阶段。直接在 g24 的 talk 阶段调用就可结束；构造 after 存档但没有本战阵容/胜利证据，restore 后也能完成 g24、gBad2、e14。普通网页点击交互在 battle 时会被挡住，因此未证明自然 UI 可触发直接调用；风险主要是不完整/陈旧存档被当作已完成战斗。g20 的 `repeatRefusal` 同样不受 singleChoice 或 refusalRule 的完成保护：无任何答复的 after 存档可直接进入 g21 并发奖励。

结局目前由 `chooseEnding` 读取少量 flags，而不核对终局任务和历史答复证据：

| 恢复/终局夹具 | 当前结果 |
| --- | --- |
| g24，`choices.g23=1`，`firstWoman=mei` | three，符合现网页规则 |
| g24，`choices.g23=1`，缺 `firstWoman` | reunion，与已有选择记录矛盾 |
| gBad2，`forsake=true` | zhen_good，符合现网页规则 |
| gBad2，缺 `forsake` | reunion，与悲剧任务前置内容矛盾 |
| e14，`evil=2` / `evil=3` | family / alone，符合现网页阈值 |

当前 restore 只为“正在进行”的单次选择修复 assignments，不会在已到 g24 时用已记录的 g23 答案恢复缺失 firstWoman；终局默认 reunion 也不保留未知。不能据此认定所有真实旧档都会错，因为完整历史 flags 的迁移检查没有发现此故障。

建议：为当前格式的每个最终战保存独立结果证据；明确旧版已完成战斗的历史兼容合同，不能简单新增旗标后卡死旧档或凭游标补造新演出。对已有确切选择但缺少静态分支字段的存档只恢复该分支赋值，不能重发好感/奖励；真正未知的历史不应静默伪造首谈对象。终局任务必须与所属分支相容。g20 的旧 after 状态需要分别识别已记录接受、未终结拒绝和 4 拒，不能一律放行或一律重扣。

## 确认没有失败的有界检查

- g20 在 0、1、2、3 次拒绝后接受，途中每次序列化/restore，均进入 g21，`forsake=false`，好感为 `2 - 拒绝次数`，只领取一次 65 经验/15 银默认任务收益。四次拒绝逐次恢复后进入 gBad1，前三次不发任务收益，第 4 次只发一次。
- g23 两种合法选择分别保留 zi / mei，正常终局映射正确。这里仅说明状态映射，不解决上文人物先后和同行演出的缺失。
- g24、gBad2、e14 完成后再次调用完成方法不会重复发任务奖励；`completed` / `done` / `claimedRewards` 的完成后幂等没有在本审计中失败。
- revision 1–12 × 7 个后段任务（g16、g20、g23、g24、gBad1、gBad2、e14）× 数字索引/稳定 ID 共 168 个内存旧档夹具，任务身份、已有拒绝数、firstWoman、g23 选择、evil、钱、经验和领取记录均保留。它不是这些版本所有旧档形态的穷举，也没有把缺字段的存档误归为已通过。
- 既有 `validate-choice-transactions.mjs` 只覆盖 g20 连续四拒；`validate-long-journey.mjs` 验证路线能到结局，但自动调用引擎，没有检查当前人物名单、每次点击结果中途刷新、首谈对象、普通失败重试收益或不完整终局证据。`validate-story-ui.mjs` 的致死答复提交断言重点在 e05/e07，不能替 g20 兜底。
